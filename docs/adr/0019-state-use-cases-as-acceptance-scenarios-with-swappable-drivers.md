# State use cases as acceptance scenarios with swappable drivers

Our use cases are spread over `src/core/*.test.ts` and `src/lcd/screen-model.test.ts`, written against `reduce`, raw state and the screen model, and none of them can run against the real UI. From now on each use case is stated once, as a scenario in `acceptance/scenarios/`, through a `Window` of `{ trainee, see, time }`. The setup follows order-processor's ADR "Acceptance scenarios with swappable drivers".

1. **One scenario, swappable drivers.** A scenario imports no runner. An in-process driver runs it today; a Playwright driver can run the same scenario later. A use case written once cannot drift between a core version and a UI version. The cost: every step and observation needs one implementation per driver, and a scenario may use only what every driver can do.
2. **The in-process driver runs `core`, `world` and the LCD screen model.** It dispatches to `reduce`, holds Tallys through the Roster, moves time through the simulation clock, and reads the LCD through `screenText`. We rejected a driver over `core` alone: the manual and our ADRs state behaviour as what the LCD shows, and selectors cannot say that.
3. **The Trainee's steps are physical.** The `Window` offers only what the Trainee does with hands: press or hold a Key, hold a Tally to Check, and the clock controls. Readable recipes such as `logIn(window, …)` live in `acceptance/` and are composed from those steps, so each driver implements only a few steps and every recipe runs on every driver. We rejected intent-level steps on the `Window` (`trainee.logIn(…)`): every driver would reimplement each one as a key sequence, and the key-by-screen navigation ([Define the key-by-screen navigation model](0004-define-the-key-by-screen-navigation-model.md)) would hide behind them.
4. **The LCD is observed as text.** `see.lcd().reads([…])` checks the whole screen, line by line, each line a string or a `RegExp`; `see.lcd().shows(…)` checks a single line; `see.lcd().isOff()` checks `Display aus`. The device wording stays in the scenarios, where it can be checked against the manual, and the Playwright driver can answer from the LCD's `aria-label`. Domain-shaped observations (`see.trupp(1).isInAlarm()`) may be added later where text matching gets clumsy, not before.
5. **The Alarm-LED stands for the siren.** `see.alarmLed()` is blinking or off. There is no siren observation: the UI shows nothing of the siren beyond the LED, which follows the same selector, and the mute toggle belongs to the simulator, not the device. We rejected a visible siren indicator added only for tests.
6. **`time.passes` is real time.** Simulated time follows the simulation clock: 1× at the start, then whatever the Trainee sets with `trainee.setSpeed(…)`, `trainee.pause()` and `trainee.play()`. This is how the Trainee experiences time, it keeps the drop to real time ([Drop the simulation to real time while an Alarm sounds](0017-drop-the-simulation-to-real-time-while-an-alarm-sounds.md)) and pause testable as scenarios, and it maps onto Playwright's `page.clock`. We rejected `time.passes` as simulated time, which would hide the speed control.
7. **Every scenario starts on a fresh simulator, Checkbox off.** First-launch defaults accepted, the default Roster, `Display aus`. Tallys are named by Kurzname and Role (`{ fahrzeug: "HLF", role: "Angriffstruppführer" }`), as the Trainee reads them on the Roster and the LCD. Anything else is set up by Trainee steps. We rejected a starting state passed in by the scenario: the Playwright driver could only honour it by seeding storage.
8. **Observations only through the screen, with no escape hatch to raw state.** No call returns state, not even "just for this test". A single escape hatch would split the suite into scenarios both drivers can run and scenarios only one can, and nobody would notice. The cost: a rule the screen cannot show stays a core test, so `acceptance/` is not the whole story of what the core enforces.
9. **Every step and observation is async**, though `reduce` and the screen model are synchronous. Playwright is async, and a synchronous DSL would mean rewriting every scenario when its driver arrives. A missing `await` is caught by `no-floating-promises`.

## Considered options

- **Gherkin (Cucumber).** Rejected: new tooling and a step-matching layer, where plain TypeScript calls need neither.
- **A Playwright driver in the first slice.** Rejected for now: a bigger first slice, and rAF-driven ticks under `page.clock` would force precision trade-offs before any scenario needs them. It follows as its own ticket; until then the `e2e/` specs stay.
